## 1. Фикстуры

| ID | Содержание |
| --- | --- |
| C1 | Atlantic Studio, Lda.; представитель Sofia Costa; учредитель Alex Moreno; деятельность — разработка ПО; все данные синтетические |
| E1 | Регистрационная выписка с названием/номером; E2 — учредительный документ; E3 — ID представителя; E4 — описание деятельности |
| E5 | Документ адреса деятельности отсутствует в начальном наборе; E6 — схема владения появляется после запроса B |

Фикстуры должны содержать точные выдержки, URL вида `https://example.test/...`, `retrieved_at`, идентификатор источника и признак `synthetic`. Для живого банковского сценария создаётся отдельная версия после фактчекинга, без копирования условных требований на реальные банки.

## 2. Сквозные и функциональные кейсы

### TC-01 — профиль переиспользуется в двух пакетах [U1, U3; P0]

**Дано:** C1, E1–E4. **Когда:** пользователь сохраняет профиль, выбирает A/B и формирует пакеты. **Тогда:** юридическое имя и номер берутся из одной версии профиля; оба пакета ссылаются на E1; ручные поля отмечены как ручные; повторного ввода для B нет. **Критерий провала:** два расходящихся значения одного факта без явной версии/источника.

### TC-02 — неизвестный UBO остаётся неизвестным [U1; P0]

**Дано:** в E1–E4 нет подтверждения статуса UBO. **Когда:** анализируется профиль. **Тогда:** статус факта `unknown`; система предлагает получить доказательство. **Провал:** `verified` только из текста, сгенерированного моделью.

### TC-03 — противоречивые документы [U1; P0]

**Дано:** E1 и E2 содержат разные адреса деятельности. **Когда:** система извлекает адрес. **Тогда:** видны оба значения и их документы; факт требует подтверждения пользователя; пакеты, зависящие от адреса, не получают `ready`. **Провал:** молчаливый выбор одного значения.

### TC-04 — источники требований прослеживаются [U2; P0]

**Дано:** SA и SB. **Когда:** пользователь открывает требования. **Тогда:** каждая позиция имеет маршрут, URL, конкретную выдержку, время получения и ID источника; клик открывает соответствующую страницу/сохранённую выдержку. **Провал:** позиция со статусом «опубликовано банком» без источника.

### TC-05 — условие только конкретного канала [U2; P0]

**Дано:** SA содержит ограничение онлайн-канала; профиль C1 не подтверждает прохождение условия. **Когда:** сравниваются A/B. **Тогда:** A получает `check_directly` или `not_supported_by_published_route` в зависимости от точной формулировки фикстуры; B не наследует ограничение; нигде нет вывода «банк A откажет». **Провал:** банковский отказ или перенос ограничения на B.

### TC-06 — два существенно разных пакета [U3; P0]

**Дано:** C1, E1–E4, SA/SB. **Когда:** формируются A/B. **Тогда:** A содержит E5 как `missing`, B содержит E2/E4 как `ready`; у каждого пункта требование, источник, документ/пробел, обоснование. **Провал:** одинаковые универсальные списки либо скрытый E5.

### TC-07 — отсутствие документа не маскируется [U3; P0]

**Дано:** A требует E5; E5 отсутствует. **Когда:** пользователь открывает пакет A и экспортирует его. **Тогда:** E5 остаётся `missing`, общий пакет «есть открытые вопросы», пункт виден в экспорте. **Провал:** пакет помечен полностью готовым.

### TC-08 — выдуманное требование модели [U2, U3; P0]

**Дано:** подставлен результат анализа с дополнительным «обязательным сертификатом», отсутствующим в SA/SB. **Когда:** валидируется ответ. **Тогда:** требование отклонено или явно помечено как неподтверждённое и не повышает готовность пакета. **Провал:** появляется как опубликованное правило банка.

### TC-09 — источник устарел или недоступен [U2, U5; P0]

**Дано:** живой запрос завершился ошибкой; есть сохранённые SA/SB с датой. **Когда:** пользователь обновляет требования. **Тогда:** интерфейс показывает ошибку, возраст данных и действие «проверить напрямую/повторить»; пакет не называется проверенным сейчас. **Провал:** сохранённое содержимое имеет метку `fresh`.

### TC-10 — конфликт двух страниц [U2; P0]

**Дано:** две публикации одного маршрута различаются по обязательности E5. **Когда:** система обновляет требования. **Тогда:** позиция `uncertain`, обе выдержки доступны, пакету требуется ручная проверка. **Провал:** случайный выбор более удобной позиции.

### TC-11 — запрос банка меняет только релевантное [U4; P0]

**Дано:** утверждённый пакет B v1, F1, затем E6. **Когда:** пользователь добавляет E6 и пересчитывает пакет. **Тогда:** создан B v2; требование владения и черновик ответа обновлены; видно до/после, E6 и автор подтверждения; A не меняется, если общие факты не исправлены. **Провал:** v1 перезаписана либо A изменилась без зависимости.

### TC-12 — новое противоречие блокирует уверенный ответ [U4; P0]

**Дано:** E6 противоречит владельцу в профиле. **Когда:** система формирует ответ на F1. **Тогда:** расхождение видно, ответ содержит неопределённость/требует разрешения; не создаётся утверждённый пакет. **Провал:** уверенный ответ с любой из конфликтующих версий.

### TC-13 — подтверждение перед экспортом ответа [U4; P0]

**Дано:** есть черновик ответа. **Когда:** пользователь нажимает экспорт без подтверждения. **Тогда:** экспорт заблокирован; после просмотра, редактирования и явного подтверждения экспорт содержит версию и время одобрения. **Провал:** скачивание черновика как утверждённого либо отправка в банк.

### TC-14 — изменение общего факта инвалидирует пакеты [U1, U3; P0]

**Дано:** A v1 и B v1 одобрены; пользователь меняет адрес C1. **Когда:** сохраняется новая версия профиля. **Тогда:** оба зависимых пакета помечены `needs_recalculation` и прежние одобрения не переносятся на новые версии. **Провал:** экспорт нового факта под старым утверждением.

### TC-15 — сбой модели и некорректный JSON [U3, U5; P0]

**Дано:** тайм-аут, затем ответ с отсутствующим `source_id` или неверным статусом. **Когда:** пользователь формирует пакет. **Тогда:** понятная ошибка и возможность повтора; неподтверждённый пакет не выдаётся за готовый, прошлый одобренный результат остаётся неизменным. **Провал:** частичный результат опубликован как успешный.

### TC-16 — повтор действия и новая сессия [U5; P0]

**Дано:** C1, два пакета и F1. **Когда:** пользователь обновляет страницу, повторяет запрос после сбоя и открывает пример в новой сессии. **Тогда:** версии не дублируются от повторной команды; можно пройти U1–U4 без персональных данных и скрытых действий разработчика. **Провал:** потеря связей или двойной запрос в истории.

## 3. Контракт проверки AI-результата

На вход анализу передаются только версии профиля, доказательств и ограниченный набор датированных источников с ID. На выходе каждый пункт обязан иметь `requirement_id`, `source_id`, `evidence_ids[]`, `status`, `rationale`; каждый ID сверяется кодом со входом. Новое требование без источника не становится фактом. Для `ready` требуется релевантный `evidence_id`; для `not_applicable` — ссылка на подтверждающий факт. Отказ схемы, неизвестный ID или конфликт переводит результат в ошибку/ручную проверку. При повторе фиксируются версии входов, чтобы результат нельзя было приписать другому набору данных.
