# Business Banking Navigator — TDPD v0.1

> Новая цель от 6 октября 2026: подбор банковского обслуживания под задачи бизнеса. Актуальный план и аудит: [TDPD-selection-2026-10-06.md](TDPD-selection-2026-10-06.md). Прежние требования/сценарии/TC ниже сохраняются для подготовки документов; они не подтверждают готовность подбора.
**Дата:** 1 октября 2026. **Статус:** рабочая спецификация продукта. Название временное.

TDPD = Test-Driven Product Development. Сначала описываем наблюдаемую потребность и критерии принятия результата, затем проектируем и реализуем. Рабочий цикл: **Problem → Constraints → Solution → Validation**. В каждом решении фиксируем **контекст, выбор и способ проверки**.

## 0. Короткое решение

Создаём рабочее место для малого бизнеса, который готовится открыть корпоративные счета в нескольких банках: один профиль компании и набор документов превращаются в отдельные проверяемые пакеты по требованиям каждого банковского маршрута. Когда банк запрашивает дополнительную информацию, пользователь обновляет профиль один раз и видит, что изменилось в пакете. Отправку и окончательное решение контролирует человек и банк соответственно.

**Первая задача:** подготовить два пакета для одной португальской SME с иностранным учредителем и ответить на один дополнительный запрос. Это первая проверяемая задача, а не обещание полной банковской инфраструктуры компании.

## 1. Problem — потребность и граница знания

### 1.1 Кто пользователь

- **Основной:** основатель или операционный менеджер новой SME в Португалии, который собирает документы для открытия счёта.
- **Второй кандидат на покупателя/повторного пользователя:** бухгалтер или консультант, который проводит много компаний через такие процессы. Не считаем этот сегмент подтверждённым до интервью.
- **Не пользователь продукта в первом срезе:** сотрудник банковского KYB. Он может получить подготовленный компанией пакет, но для него не строим интерфейс принятия решений.

### 1.2 Job to be done

«Когда мне нужно подать заявки в несколько банков, я хочу понять требования каждого маршрута, собрать общую информацию о компании один раз, увидеть пробелы и получить отдельный пакет для каждого банка, чтобы не терять время на повторную подготовку и не заявить то, чего мы не можем подтвердить».

### 1.3 Текущий процесс и боль, которую проверяем

Предполагаемый процесс: открыть сайты банков → выяснить, какой маршрут доступен → вручную сопоставить перечни документов → повторно вводить данные → подать заявки самостоятельно → обработать дополнительные запросы из почты или портала. Различия опубликованных требований наблюдаемы; насколько часто компании одновременно обращаются в два банка, сколько времени уходит и готовы ли платить за помощь, пока **не подтверждено**.

### 1.4 Исходы для пользователя

1. Понимать, что опубликовано банком, к какому маршруту относится и когда проверено.
2. Видеть для каждого требования: подтверждено документом, отсутствует, неясно или неприменимо.
3. Переиспользовать факты и документы, но получить отдельный пакет для каждого банка.
4. Исправить один факт/документ и понять, какие пакеты и ответы надо обновить.
5. Одобрить экспорт; не обнаружить, что продукт сам отправил заявку.

## 2. Constraints — ограничения и принципы доверия

| Ограничение | Следствие для продукта |
| --- | --- |
| Публичная страница может описывать только онлайн-маршрут | Показываем ограничение маршрута; не объявляем компанию неприемлемой для банка целиком |
| Банк может запросить больше, чем перечислено публично | Пакет называем «готовым по известным опубликованным требованиям», сохраняем статус `uncertain` |
| Источники меняются или недоступны | Храним ссылку, выдержку, дату и тип данных: получены сейчас или сохранены ранее |
| Ошибочная уверенность вредна | Нельзя ставить `ready` без связанного доказательства; новая модельная «норма» без источника требует проверки |
| Файлы содержат чувствительные данные | В разработке и демонстрации используем синтетику; ключи держим на сервере; правила хранения реальных файлов проектируем отдельно |
| Нет партнёрских банковских API | Готовим пакет и экспорт, а пользователь самостоятельно проходит банковский маршрут |
| Пользователь отвечает за решение | Перед экспортом изменений и ответа на запрос требуется явное подтверждение |

**Не делаем в P0:** прямую подачу в банк, автоматическую регистрацию компании, гарантии открытия счёта, юридическое заключение, сквозную интеграцию с KYC банка, универсальное покрытие всех стран и банков.

## 3. Solution — продуктовая модель

### 3.1 Состав продукта

| Объект | Что содержит | Что пользователь делает |
| --- | --- | --- |
| Профиль компании | Юрлицо, деятельность, представители, владельцы, происхождение фактов | Заполняет и корректирует |
| Библиотека доказательств | Документы и извлечённые поля, привязка к фактам | Добавляет, заменяет, подтверждает |
| Банковский маршрут | Канал подачи, опубликованные условия и дата источника | Сравнивает применимость |
| Требование | Формулировка, условие, ссылка на источник | Проверяет корректность трактовки |
| Пакет банка | Требования, статус, связанные факты/документы, нерешённые вопросы | Дорабатывает и утверждает экспорт |
| Дополнительный запрос | Текст запроса, затронутые требования, версия ответа | Добавляет данные и подтверждает ответ |

### 3.2 Главный сценарий U1: два банка

1. Пользователь открывает пример компании или создаёт профиль.
2. Выбирает два конкретных банковских маршрута.
3. Система получает публичные страницы и показывает источник/дату каждой найденной позиции.
4. Система формирует два разных списка: что готово, чего нет, что надо уточнить непосредственно у банка.
5. Пользователь открывает каждое заключение и видит связанный документ и источник банковского требования.
6. Пользователь утверждает экспорт двух пакетов/чеклистов и сам использует их при подаче.

**Альтернативы:** источник не открылся → показываем датированные сохранённые сведения и требуем повторной проверки; условие относится только к онлайн-каналу → предлагаем уточнить другой канал; документа нет → оставляем `missing`, не скрываем пробел.

### 3.3 Сценарий U2: дополнительный запрос

1. Пользователь вставляет обезличенный текст запроса банка.
2. Система показывает, к каким требованиям/утверждениям он относится и чего не хватает.
3. Пользователь добавляет факт или документ.
4. Система пересчитывает затронутый пакет, показывает изменение относительно прежней версии и черновик ответа.
5. Пользователь исправляет и явно утверждает экспорт. Автоматической отправки нет.

### 3.4 Правило статусов

- `ready`: требование имеет применимое подтверждение, пользователь может его открыть.
- `missing`: доказательства нет или известно, что нужный факт не предоставлен.
- `uncertain`: условие, трактовка, свежесть источника или доказательство неоднозначны.
- `not_applicable`: имеется подтверждённое основание не применять требование; основание видно.

Статус пригодности маршрута отдельно от статуса пакета: `possible`, `check_directly`, `not_supported_by_published_route`. Последний означает только ограничение конкретного опубликованного маршрута.

## 4. Validation — критерии до реализации

| ID | Проверка на синтетическом кейсе | Ожидаемый результат | Приоритет |
| --- | --- | --- | --- |
| T01 | Создать профиль и открыть оба пакета | Общие факты переиспользованы; у каждого поле-источник или ручной ввод | P0 |
| T02 | Обновить требования двух маршрутов | У каждой позиции банк, маршрут, URL, выдержка и дата; сохранённые данные явно помечены | P0 |
| T03 | Дать маршрут с условием, не подтверждённым профилем | `check_directly`; нет утверждения, что весь банк отказал | P0 |
| T04 | Сгенерировать пакеты с различающимися требованиями | Два разных результата; каждый статус и доказательство открываются | P0 |
| T05 | Убрать обязательный документ | `missing`; пакет не отображается как полностью готовый | P0 |
| T06 | Подставить модельный вывод с выдуманным требованием | Нет публикации как подтверждённого факта без банковского источника | P0 |
| T07 | Добавить документ после запроса | Пересчитаны затронутые позиции, видна версия до/после | P0 |
| T08 | Попытаться экспортировать ответ без подтверждения | Экспорт заблокирован до явного действия пользователя | P0 |
| T09 | Поиск или модель недоступны | Честная ошибка/сохранённые данные с датой; нет поддельного «успеха» | P0 |
| T10 | Пройти путь с новой сессии | Полный сценарий выполняется с синтетическими данными без инструкций разработчика | P0 |

**Критерий готовности ядра:** T01–T10 пройдены, по двум банкам подготовлены проверяемые пакеты, один дополнительный запрос приводит к осмысленному изменению и одобренному человеком экспорту.

### 4.1 Проверка самой потребности

Провести минимум пять интервью с основателями и бухгалтерами, которые недавно открывали бизнес-счёт. Просить показать последовательность реальных действий и повторных запросов; фиксировать число банков, документы, затраты времени, точки отказа, обходные решения и кто оплачивает помощь. Искать опровержения: один банк всегда достаточен; документы редко повторяются; бухгалтер уже решает задачу без существенных затрат.

**Решение по итогам:** если повторяемость и цена боли не подтверждаются, не расширять банк-лист и архив документов; пересмотреть сегмент или задачу. Целевые проценты экономии и TAM до замера не заявляем.

### 4.2 Метрики пилота

- Время от начала до двух пакетов, число повторно введённых полей, число нерешённых требований.
- Доля заключений с корректно доступным источником; количество найденных пользователем ложных уверенных выводов.
- Время обработки дополнительного запроса и доля случаев, когда человек исправляет предложенный ответ.
- Для сегмента бухгалтеров: число компаний на специалиста в месяц и готовность платить, только по интервью/пилоту.

## 5. Техническое решение для первой реализации

Технология служит сценариям U1 и U2. Сервер вызывает **Tavily Search/Extract** для публичных страниц банков и **NVIDIA Nemotron 3 Super через Nebius Token Factory** для структурирования требований, сопоставления с фактами и подготовки объяснения/черновика. Фактическую доступность model ID `nvidia/nemotron-3-super-120b-a12b` проверяем при настройке. Это выбор текущей реализации, а не формулировка потребности пользователя.

**Пайплайн:** источник → нормализованные требования с source ID → профиль и доказательства → модельный кандидат сопоставления → проверка схемы и ссылок кодом → проверяемый пакет → подтверждение человеком. Модель не получает право отправлять сведения в банк и не может создать подтверждённое требование без источника.

**Минимальные контракты:** `CompanyProfile`, `Evidence`, `BankRoute`, `Source`, `Requirement`, `PackageItem`, `FollowUp`, `PackageRevision`, `Approval`. Для каждого заключения храним входные ID и версию результата. Ключи API только на сервере. Для примера используем синтетические данные.

## 6. Порядок работ и зависимости

| Шаг | Результат | Условие перехода |
| --- | --- | --- |
| 1. Фактчекинг | Два выбранных банка, точные публичные страницы, различия маршрутов, датированные выдержки | Есть безопасный синтетический сценарий без приписанной банкам политики |
| 2. Контрольный пример | Фикстуры компании, документов, дополнительного запроса и ожидаемый результат T01–T10 | Сценарий можно проиграть вручную |
| 3. Продуктовый каркас | Экран профиля, сравнения, пакета и запроса; хранилище версий | Пользователь проходит путь на фиксированных данных |
| 4. Живые сервисы | Получение источников и структурированный анализ на текущих входах | Видны реальные вызовы, валидный ответ и понятный сбой |
| 5. Доверие и экспорт | Проверка ссылок, статусов, история, подтверждение и экспорт | T01–T10 проходят в интерфейсе |
| 6. Discovery и пилот | Интервью и наблюдение нескольких реальных процессов | Можно уточнить сегмент, ценность и P1 |

**P1 после ядра:** третий банк, рабочее место бухгалтера для нескольких клиентов, извлечение данных из загруженных PDF, напоминания об истечении документов и регулярное обновление источников. Каждое расширение требует подтверждения соответствующей боли.

## 7. Открытые решения

1. Какие именно два банка и маршрута дают честное, различающееся сравнение? Проверить публичные страницы перед фиксацией примера.
2. Кто первый пользователь: основатель с разовым кейсом или бухгалтер с повторяющимся процессом? Интервью решают приоритет, технический сценарий пока совместим с обоими.
3. Какой минимальный полезный экспорт: проверяемый чеклист и приложенные файлы, печатная страница или PDF? Решить на первом пользовательском просмотре.
4. Как хранить реальные документы после синтетического среза? Отдельное решение по безопасности и согласию, прежде чем загружать персональные данные.
