# Business Banking Navigator: подбор банковского обслуживания — TDPD v0.2

Дата: 6 октября 2026. Статус: план и аудит покрытия, не разрешение на реализацию всех пунктов. Новая цель согласована в разговоре; правила ранжирования, архитектурные изменения и приёмка ещё не утверждены. TDPD / Test-Driven Product Development — оригинальный метод Иннокентия Бодрова.

Этот документ задаёт новую продуктовую рамку. TDPD.md v0.1 и его U/TC сохраняются как история и спецификация подготовки пакетов. Здесь новые идентификаторы SEL; старые 64 TC не перенумеровываем и не объявляем выполненными. Приложение в этом проходе не менялось.

## 1. Проблема, пользователь и результат

**Проблема:** предпринимателю сложно выбрать банковское обслуживание под реальные операции и ограничения бизнеса. Возможности, условия доступа и тарифы трудно сопоставить; пользовательский опыт разрознен. Список документов не отвечает на вопрос «какой вариант подходит мне и почему».

**Первый пользователь (рабочая гипотеза):** основатель/операционный менеджер компании Португалии, выбирающий основной или дополнительный бизнес-счёт. Консультант — вторичный сегмент; повторяемость и платёжеспособность обоих ещё не доказаны. География первого среза — PT; банки и цифровые платёжные сервисы. Личные счета и фрилансеры требуют отдельных условий/маршрутов, не подменяют Lda.

**JTBD:** «Когда мне нужно организовать банковские операции бизнеса, я хочу описать свои задачи и ограничения, сравнить доступные варианты по реальной пригодности и затратам, понять компромиссы и выбрать следующий шаг».

**Результат:** обоснованный короткий список до трёх вариантов; при недостатке данных — список для уточнения либо честное отсутствие подходящих вариантов. Одна связка из двух провайдеров допустима только при показанном дополнительном эффекте и полной стоимости, не по умолчанию. После выбора — маршрут открытия, вопросы банку, документы и существующий package workflow.

**Сигналы успеха:** время до обоснованного списка и действия; число ошибок по обязательным потребностям; доля утверждений с подходящим источником; способность человека объяснить выбор и компромисс; число уточнений/исправлений; завершение пути. Не обещаем экономию или процент успешного открытия без замера. Предложение для UAT: пять наблюдаемых сессий, в четырёх человек самостоятельно объясняет выбор/ограничения и следующий шаг; ноль подтверждённых рекомендаций с нарушением обязательного условия. Это критерий пилота, не уже полученный результат.

### Риск зависимости

Пользователь может потерять время/деньги, отказаться от пригодного банка или неверно понять доступность средств. Ошибка выбора обратима не мгновенно: открытие и переход требуют усилий. Особые случаи: иностранные владельцы, нерезиденты, сложная структура, неподдерживаемые отрасли, слабые цифровые навыки. Система не открывает счета, не перемещает деньги и не обещает решения банка. Неизвестный факт не становится отказом или согласием; отзывы не доказывают KYC-пригодность. Реальные документы, кредитное одобрение и операции с деньгами за границей первого среза.

## 2. Модель и проверяемые правила

### Потребности

Форма компании, регистрация/фактическая деятельность, отрасль/CAE, страны и роли участников; страны клиентов/поставщиков; входящие/исходящие валюты; примерные месячные суммы и количество платежей; число пользователей/карт; местные платежи/Multibanco/MB WAY/налоги; онлайн/отделение, язык поддержки, интеграции, наличные; бюджет; кредит как заявленная потребность без прогнозирования approval. Каждая потребность: mandatory / preference / irrelevant; unknown разрешён. Нулевой объём отличается от неизвестного. Оборот не требует реальных банковских выписок.

### Каноническая модель (предложение архитектуры)

`BankingDecisionCase` — основная сущность: версия компании + версия потребностей + evidence baseline + policy version → неизменяемый `RecommendationSnapshot` → выбранный вариант → связанные `PackageSnapshot` и follow-up. Состояния: draft → needs_information или assessed → shortlisted → chosen → preparation. При смене входов/источников/правил прежняя рекомендация stale; старый снимок сохраняется. package approval не утверждает правильность рекомендации или решение банка.

`Provider` отдельно от `AccountProduct` и `OpeningRoute`. Возможность продукта не переносится на все продукты банка. Условия online не означают отказ branch. `CapabilityFact`, `FeeRule`, `EligibilityRule`, `ReviewSignal` ссылаются на конкретные источники и область. Таблица, поиск, импорт и модель используют одну утверждённую базу; автоматический refresh создаёт кандидатов, не переписывает её.

| Правило | Внешне наблюдаемое поведение |
| --- | --- |
| R01 | Пользователь видит, какие обязательные поля не заполнены; неизвестные данные сохраняются без выдумывания |
| R02 | Доступность маршрута: confirmed mismatch / potentially suitable / needs confirmation. Не гарантировать открытие |
| R03 | Отдельные статусы для eligibility, обязательных возможностей и document readiness; готовый пакет не улучшает suitability |
| R04 | Mandatory feature с confirmed unsupported исключает из подходящих; unknown/conflict переводит в уточнение, не в подтверждённый список |
| R05 | Preference влияет на порядок только при известном факте; отсутствие данных не считается плохим качеством |
| R06 | У каждого сравниваемого факта есть продукт, страна, канал, URL/выдержка, дата, authority и approval; stale/conflict явно видны |
| R07 | Не использовать опубликованные тарифы без даты/плана/единиц; показывать формулу, включённые лимиты, налоги/FX и неизвестные компоненты |
| R08 | Оценка расходов основана на заданном объёме; неполная сумма называется известной частью, не полной стоимостью |
| R09 | Отзывы — отдельный слой опыта: страна, business/personal, дата, тема, выборка. Нет отзывов ≠ плохой банк; личные отзывы не превращаются в бизнес-оценку |
| R10 | Повторы/накрутка/малые выборки отмечаются; не выводить вероятность блокировки/открытия из отзывов |
| R11 | Предложенный порядок: mandatory gate → соответствие подтверждённым приоритетам → сопоставимые расходы → явные компромиссы. Веса/тайбрейк/свежесть требуют решения до RED |
| R12 | Показать основания, недостатки, неизвестные и следующий вопрос; при равенстве показывать равенство. Числовая уверенность без калибровки запрещена |
| R13 | Пара провайдеров сравнивается с одним: вклад каждого, дублирование, стоимость/дополнительные операции; отсутствие превосходства не выдаёт пару как предпочтительную |
| R14 | Смена профиля/потребностей/принятого источника инвалидирует затронутый снимок; неподтверждённый кандидат не влияет |
| R15 | Модель предлагает текст/классификацию, deterministic logic решает ограничения и стоимость; выдуманный продукт/факт/citation не проходит |
| R16 | Ошибка API не заменяет снимок; повтор/конкуренция не создают противоречивый выбор; информация восстанавливается |
| R17 | Человек выбирает вариант; shortlist не отправляет заявку и не меняет package approval |
| R18 | Никакое партнёрское вознаграждение не скрыто в порядке; если появится, явно раскрыть и отделить рекламный блок |

## 4. Пользовательская поверхность и контракт

Сохраняем существующее локальное web-приложение и стек Node/Playwright. Предложенный путь: потребности → пригодность → сравнение/расходы → опыт клиентов → выбор и действия → документы. Экраны/представления: анкета, результаты с блоком уточнений/исключённых, подробное сравнение, источники/отзывы, выбранный вариант и подготовка. Loading/empty/unknown/conflict/stale/error/retry обязаны иметь самостоятельный текст и действие. Клавиатура, labels, фокус, мобильный экран, доступность источников входят в UI acceptance.

Новые API и хранение — пока проектируемые, не существующие: save needs; assess case; get recommendation/history; choose option. Сервер владеет данными/версией оценки; клиент не присылает доверенные scores. Развёртывание не меняем без решения. Ключи server-only .env; подключение отзывов не требует browser auth, пока не обнаружен законный доступный источник. Политики доступа и хранения проверять до ingestion; запрет обхода login и массового копирования отзывов.

## 7. Очерёдность поставки

1. **Input:** 01–06,09–14,18,22. Утвердить первый сегмент/потребности, evidence baseline для малого набора, scoring и стоимость, surface/архитектуру. Можно независимо готовить интервью/публичные источники; не начинать ranking с выдуманными весами.
2. **Срез A:** анкета → eligibility/capability → обоснованный список одного провайдера. RED S01–07,10–11,15–20 → implementation → GREEN → bounded live → UAT. Переиспользуем source/session mechanisms.
3. **Срез B:** проверенный калькулятор расходов и изменение приоритетов: RED S06,08–09 и регрессия; затем GREEN/UAT. Если расходы нужны для правила порядка среза A, B становится зависимостью A; не ранжировать цену до готового calculator.
4. **Срез C:** отзывы как контекст и пара провайдеров: 27–34/S12–14. Отзывы не блокируют первый полезный срез; до него UI честно не заявляет «учтён опыт клиентов».
5. **Срез D:** выбор → подготовка документов, сохранение новой canonical сущности, регрессия старых TC и UAT.
6. **Release:** 41,45–53. Подготовка автономна; публикация и финальная подача требуют отдельных решений. Real-data P2 не смешиваем с synthetic release.

## 8. Открытые решения и гейты

| Решение | Предложение до утверждения | Что блокирует |
| --- | --- | --- |
| D01 Первый сегмент | Founder/operator PT Lda; consultant позже | Окончательную анкеты/UAT постановку |
| D02 P0 результат | Один провайдер; до 3 кандидатов; пары P1 | S10/S12 и UI contract |
| D03 Scoring | Mandatory gate, затем объяснимые preferences; без общего «рейтинга банка» | RED порядка; веса/тайбрейк не определены |
| D04 Reviews | Отдельный контекст, не numerical score | Review influence/ingestion до выбора источников |
| D05 Baseline и freshness | Небольшой проверенный набор, field-specific freshness | Official rules/costs acceptance |
| D06 Durable case | Новый DecisionCase со ссылками на существующие snapshots | Production schema/API и migration compatibility |
| D07 Кредиты/бюджет/публичный host | Санитизированный учёт, bounded calls | Public release; счета/покупки не делаем автоматически |

**Input:** partial (цель принята, ranking/costs/сегмент не доведены). **Surface:** existing shell проверен, новый journey proposed. **Evidence:** opening-doc baseline частичный, capability/fees/reviews отсутствуют. **Reliance:** классификация выше, edge scenarios planned, достаточность contextual evidence предстоит принять. **RED:** нет. **GREEN:** только прежний documentary/comparison slice, новый подбор отсутствует. **Output/UAT:** нет по новой цели. Поэтому продукт «подбирает банк под задачи бизнеса» пока не готов, независимо от числа прежних тестов.

Полезность оцениваем отдельно от технической корректности: интервью могут изменить сегмент и порядок; это не повод выбрасывать проверенный механизм документов. После каждого среза обновляем цепочку R → S → test path/run → snapshot/UI proof → human verdict.
